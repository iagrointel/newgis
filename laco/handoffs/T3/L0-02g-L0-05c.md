### O gap: a tela de detalhe não reconecta

O servidor força o fim de **qualquer** conexão SSE aos 30 minutos, mesmo que o job continue rodando
(`app/jobs/eventos.py`):
```
24: DURACAO_MAX_S = 1800
142: yield _sse("fim", {"id": jid, "estado": job["estado"], "motivo": "tempo máximo da conexão (30 min); reconecte"})
```
Note que `estado` aqui é o estado **real e corrente** do job (pode ser `"rodando"`), não um estado
final — o próprio comentário do módulo (linha 3) chama isso de "30 min no máximo", esperando que
quem recebe o evento `fim` decida se deve reconectar.

**A tela de lista se recupera sozinha** (`web/js/jobs/lista.js`):
```
158-165: atualizarLinha(job) { ... if (!FINAIS.has(job.estado)) assinaturas(); }
222-236: assinaturas() { ...para cada job ativo que não está em s.assinados, assinar(id, ouvinte)... }
```
Como o evento `fim` forçado chega com `estado: "rodando"` (não-final), `atualizarLinha` dispara
`assinaturas()` de novo, que enxerga o job como "ativo mas sem assinatura" e reabre o SSE (ou cai
pro polling) na hora. A lista nunca fica muda.

**A tela de detalhe não.** `web/js/jobs/detalhe.js`:
```
137-155: function ouvinte(ev) { ...
  } else if (ev.tipo === 'fim') {
    if (ev.dados) s.job = ev.dados;
    renderizarCabecalho();
    mostrarModo(null);          // <- só apaga o indicador "ao vivo"/"atualização a cada 3s"
  } ...
}
227: if (!FINAIS.has(job.estado)) assinar(id, ouvinte);   // só roda dentro de abrir(), 1 vez
```
`assinar()` só é chamado uma vez, na abertura do painel (`abrir(id)`, linha ~200-227). O `ouvinte`
nunca verifica `FINAIS.has(s.job.estado)` para decidir se deve reabrir a assinatura — ele só
esconde o marcador de "ao vivo". Resultado: **qualquer job que passe de 30 minutos de execução,
visto pela tela `/tarefas/<id>`, para de atualizar silenciosamente aos 30 min**, mesmo que o job
real continue rodando por mais 1h30 (o cenário exato da refutação, "aba aberta 2h"). Não há erro
de console, não há aviso ao usuário — a tela só congela.

Isso não foi reproduzido ao vivo nesta sessão (precisaria de um job de >30 min de verdade ou
monkeypatch de `DURACAO_MAX_S` no processo real do `plat-api`, que está rodando como serviço — mexer
nisso com a RAM da máquina do jeito que está agora não é prudente). A leitura de código acima é
determinística o bastante (mesma classe de evidência que o handoff `L0-02-bcd-verificacao.md` já
usou para o caso "1.000 senhas em 3 min", registrado ali como "leitura de código, não medição").

**Conserto sugerido (para a trilha de frontend, fora do escopo desta verificação):** em
`detalhe.js::ouvinte`, no ramo `'fim'`, checar `FINAIS.has(s.job?.estado)`; se não for final,
chamar `assinar(s.id, ouvinte)` de novo em vez de só `mostrarModo(null)` — o mesmo padrão que
`lista.js::atualizarLinha` já usa.

**Conclusão:** o mecanismo inteiro do portão está provado (todas as cláusulas literais do portão
passam, herdadas do L0-05-jobs), mas a refutação — que é parte do próprio item — encontra um
defeito real e específico da tela de detalhe. **Não fechado como `entregue`.** Estado gravado como
`parcial`, com o gap nomeado e o caminho do conserto apontado; a medição de 100 mil jobs fica como
pendência não-bloqueante registrada.
