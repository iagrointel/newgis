### Gap real encontrado e corrigido (não estava no pedido original, achado ao testar)

`apagar_usuario` (app/auth/rotas_usuarios.py) só recusava por GRUPOS possuídos (`_grupos_do_dono`).
`plat.item.dono_id` é `int NOT NULL REFERENCES plat.usuario(id)` **sem `ON DELETE`** — um usuário com itens do
catálogo (mapas/camadas/pastas) na verdade fazia o `DELETE` cair num `psycopg2.errors.ForeignKeyViolation`,
traduzido por `erro_do_banco` para um `409 em_uso` GENÉRICO (nome da constraint, nunca os títulos) — não a
recusa nomeada "com a lista do que ele possui" que a hipótese do item promete e que o portão pede
("apagar usuário com 2 itens: recusa listando os 2").

**Corrigido:** `_itens_do_dono` (mesmo padrão de `_grupos_do_dono`) + checagem em `apagar_usuario` → novo erro
`409 possui_itens` com a lista de `{id, titulo}` (até 50); chave i18n `usuarios.possui_itens`; JS
(`acaoLinha('apagar')`) agora mostra a lista de títulos igual já fazia para grupos.

Provado por `tests/api/test_usuarios.py::test_apagar_com_2_itens_do_catalogo_recusa_listando_os_2`: cria 2
itens (mapa) para um editor, tenta apagar (409 `possui_itens`, títulos batem), purga os 2 itens pelo mesmo
caminho de `tests/api/catalogo/conftest.py::_expurgar_zt` (`plat.item_lixeira` + `plat.item_expurgar` via
conexão `plat_app` com contexto de admin), confirma que a exclusão passa a funcionar (204).

**Veredito: `entregue`.** Mecanismo completo, e2e cobrindo a interface inteira do portão, gap de backend achado
e fechado com teste. `docs/PARIDADE.md` (linha "gestão de membros") atualizado: continua `parcial` porque falta
um fluxo único "transferir e apagar" na MESMA tela (hoje são duas telas — Usuários e a transferência de L0-03-j
— funcionalmente completo, não integrado numa UX só); isso é ressalva de UX, não de portão.

## Adversário

Lançado agente independente (subagent_type general-purpose, sem contexto do meu raciocínio — só item, portão,
repositório e URL), instruído a derrubar os dois itens. Rodou ~22 min, 88 chamadas de ferramenta, ataques reais
contra produção (sessões de `demo`/`demo2`, inquilino temporário criado e apagado, tudo limpo ao final,
conferido por busca `q=zzz-adversario-|zt-|e2e_` = zero resíduo).

**L0-02-e: PASSA.** 43/43 casos de `test_cruzado.py` filtrados por usuarios/papeis/privilegios/eu/login/grupos;
19/19 de `test_funcoes_seguras.py`. Ataques manuais: GUC forjado em `tenant_criar` → `so_superadmin`;
`sessoes_encerrar_usuario` com tenant de demo e usuário de demo2 → `contexto_de_outro_inquilino`; varredura de
`pg_proc`/`proacl` confirmou 0 função de identidade/acesso com PUBLIC (as 2 com PUBLIC ainda vivo,
`camada_preparar`/`camada_schema_garantir`, são de `029_ingestao_vetor.sql`, de outra trilha, fora do escopo);
rota forjada sem caso cruzado (`POST /api/usuarios/{id}/rota-forjada-adversario`, testada contra uma CÓPIA de
`docs/openapi.json` no scratchpad, nunca o arquivo do repo) reprovou citando exatamente a rota forjada — a
refutação do próprio portão, confirmada.

**L0-02-f: PARCIAL → achado real, corrigido nesta sessão.** Tudo que o portão pede testar passou (editor comum
barrado em 7 rotas administrativas com 403; admin de demo nunca vê/edita/apaga usuário de demo2, sempre 404 em
7 casos; `X-Plat-Inquilino: demo2` como admin de demo → 403; único admin não se rebaixa/desabilita/apaga/lote
em 5 casos; apagar com 2 itens → `409 possui_itens` listando os 2, apagar com grupo → `409 possui_grupos`).

**Achado real (não cross-tenant, por isso `test_cruzado.py` nunca pegaria):** `POST /api/usuarios`
(`criar_usuario`) checava `so_admin_cria_admin` só por `auth.perfil`, nunca por `auth.tem("membros.papel")` —
ao contrário de `_editar()`, que já exige `membros.papel` para qualquer mudança de `perfil`/`papel_id`.
Reproduzido ao vivo: um SEGUNDO admin com papel personalizado restrito a `{membros.ver, membros.gerir}` (sem
`membros.papel`, sem `papeis.gerir`, sem `org.configurar`) conseguia criar um admin PLENO com os 46
privilégios via `POST /api/usuarios`, e também atribuir a um usuário novo qualquer `papel_id` já existente no
inquilino — inclusive um com privilégios que o próprio criador não possui. Quebra o modelo de "admin
secundário restrito" que o resto da suíte já reconhece como padrão válido (`test_privilegios_e_papeis`).

**Corrigido nesta sessão** (commit `4170a34`): `criar_usuario` agora exige `membros.papel` sempre que
`perfil != "visualizador"` ou `papel_id` é informado — o mesmo piso que `membros.gerir` sozinho já cobria
(criar no perfil mais baixo, sem papel). Novo erro `403 sem_privilegio`. Prova:
`tests/api/test_usuarios.py::test_criar_usuario_com_perfil_ou_papel_exige_membros_papel` reproduz o cenário
exato do adversário e confirma que o admin restrito só continua criando no piso depois da correção. Suíte alvo
rodada de novo (`test_usuarios`, `test_cruzado`, `test_funcoes_seguras`, `test_transferencia`, `test_eventos`,
`test_login`, `test_sessao`, `test_tokens`, `test_grupos`, `test_privilegios_declarados`): **0 falha nova**
introduzida pela correção — as 22 falhas observadas nessa rodada são 100% de OUTRA trilha regravando
`docs/openapi.json` ao vivo, sem commit ainda (ver seção abaixo).

**Achado menor, registrado mas não corrigido (decisão consciente, não bloqueante):** `POST
/api/usuarios/{id}/desbloquear` não chama `so_admin_sobre_admin` — como desbloquear só zera contador de falha
(não concede acesso nem credencial), e o ADR já documenta a rota só com `membros.gerir`, trato como design, não
falha; nomeado para quem revisar depois.

**Ressalva nomeada, fora do escopo destes dois itens:** a mesma ausência de checagem "papel_id só se o criador
tem os privilégios daquele papel" (que `_validar_papel` já impõe na CRIAÇÃO de papéis, "quem cria não concede o
que não tem") não existe na ATRIBUIÇÃO de um papel_id já existente — nem em `criar_usuario` (agora coberto
indiretamente pelo gate de `membros.papel`, mas um admin restrito COM `membros.papel` ainda poderia atribuir um
papel_id de outrem com privilégios que não tem) nem em `_editar`/`PUT /api/usuarios/{id}` (mesmo ponto,
pré-existente desde T2, não introduzido aqui). Registrado como pendência nomeada para o dono decidir se vale um
item novo (`_papel_compativel` teria de checar `set(papel.privilegios) <= set(auth.privilegios)`, não só
`perfil_minimo`) — não bloqueia a entrega destes dois itens porque o vetor CONFIRMADO e reproduzido (criar
admin pleno sem `membros.papel`) está fechado.

## Nota operacional (para quem herdar este padrão de trilhas paralelas)

Índice do git em `plataforma/enterprise` é COMPARTILHADO entre todas as trilhas do turno rodando ao mesmo
tempo. `git add <arquivos>` seguido de `git commit` sem `-- <pathspec>` explícito no commit corre risco real de
varrer `git add`s concorrentes de outras trilhas para dentro do seu commit (aconteceu 2× nesta sessão —
`app/catalogo/documento.py`/`app/main.py` via `git add MANUAL.md` genérico, depois `app/ingestao/carregar.py`
via race entre `git diff --cached` e `git commit`; ambos harmless — conteúdo real de outras trilhas, só
commit/mensagem errados, nada perdido). Nenhum arquivo foi corrompido, mas o ideal para o próximo turno é
sempre `git commit -m "..." -- <path1> <path2> ...` (pathspec explícito no commit, não só no add), que ignora o
que estiver no índice para caminhos não listados.
