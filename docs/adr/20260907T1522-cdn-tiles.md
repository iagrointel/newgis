# ADR 20260907T1522 — CDN de ladrilho: hostname separado, endereço versionado, purge por prefixo

Item: `L7-26-cdn-tiles`. Situação: aceito. Depende de `L1-02-tiles-token` (contrato de URL
`/svc/<token>/raster/<item>/{z}/{x}/{y}`, cache curto no nginx de origem, revogação com efeito em
segundos). Camada nova: uma CDN inteiramente separada da origem, na frente do prefixo de ladrilho.

## 1. Hostname separado, não o mesmo domínio da aplicação

`tiles-<x>.iagrointel.com` (nome real do subdomínio é D18/D19, ainda não fechado pelo dono) fica
**proxied** pela Cloudflare; `<x>.iagrointel.com` (a aplicação) continua **DNS-only** (decisão D19 do
laço). Misturar os dois faria a Cloudflare cachear ou distorcer chamada de API por engano de regra —
com hostname separado, "cache everything" só existe onde o hostname já é só ladrilho.

## 2. Endereço versionado no caminho, não parâmetro de consulta nem cabeçalho de validação

`GET /svc/<token>/raster/<item>@<versao>/{z}/{x}/{y}.png`, `<versao>` = os 12 primeiros caracteres do
sha256 do raster (`plat.raster_item.sha256`, que já existe desde L1-01-a — nada novo foi inventado
para dar nome a versão). Casar o sha256 vigente → `Cache-Control: public, max-age=31536000,
immutable` e `ETag` com o sha256 inteiro; não casar → 404 (a versão pedida saiu de circulação).

Por que caminho e não `ETag`/`If-None-Match`: isso exigiria o cliente revalidar a cada carga (round
trip à origem), o oposto do objetivo (a CDN nunca mais pergunta à origem por esse endereço).

**Correção à hipótese original, medida nesta bancada**: a hipótese pedia "chave de cache SEM query
string". Isso foi testado (`scripts/cdn_simulada.py`, antes da correção) e falha: pedir o mesmo
`item@versao/{z}/{x}/{y}` com `?bandas=3,2,1` (RGB) e depois com `?expressao=(b4-b3)/(b4+b3)` (NDVI)
devolvia, na 2ª chamada, os BYTES DA PRIMEIRA (`cf-cache-status: HIT`) — um cliente recebe a
renderização pedida por OUTRO cliente, sem erro visível. A versão no caminho resolve "o byte não muda
com o TEMPO"; não resolve "parâmetros de renderização diferentes produzem bytes diferentes", que é
outra dimensão do mesmo endereço. Decisão corrigida: a chave de cache é caminho + QUERY STRING
COMPLETA (o padrão de uma Cache Rule sem "ignore query string" marcado). Sem perda prática, porque o
TileJSON (item L1-02) já embute os mesmos parâmetros de renderização em todo ladrilho que um cliente
de mapa pede — dentro de uma sessão de mapa a query string nunca varia ladrilho a ladrilho.

O `TileJSON` (`/svc/<token>/raster/<item>/tilejson.json`, que continua SEM versão e com
`no-store`) já devolve a URL versionada nos `tiles[]` — o cliente de mapa nunca precisa saber que
"versão" existe.

## 3. Achado: purge por prefixo pode ser recacheado por um 200 morto

Medido na bancada (`scripts/prova_cdn.py`, `tests/medidas/L7-26-cdn-tiles.json`): a origem cacheia a
AUTORIZAÇÃO do token por `AUTH_TTL_S=2s` (`app/imagens/rotas_tiles.py`, existe desde L1-02, não é
deste item). Se o purge da CDN e a chamada seguinte caem DENTRO desses 2s depois da revogação, a
origem ainda responde 200 (a autorização em cache é anterior à revogação) e a CDN **recacheia** esse
200 por 1 ano — um único purge fica inútil.

Decisão: o procedimento de revogação PURGA REPETIDAMENTE por uma janela ≥ `AUTH_TTL_S` depois da
revogação (implementado em `scripts/prova_cdn.py`; numa conta real isso é o webhook de revogação
chamando a API de purge da Cloudflare mais de uma vez, ou esperando a janela antes de purgar uma
única vez). Alternativa descartada por ora: invalidar o cache de autorização da origem no próprio
endpoint de revogação (`app/auth/rotas_tokens.py::revogar`) — resolveria na raiz, mas acopla o módulo
de tokens ao de imagens só para este caso; registrado como possível item futuro, não feito aqui.

## 4. Purge por prefixo de CAMINHO, não por item

O prefixo de purge é `/svc/<token>/` (o token está no caminho — decisão C6 do L1). Revogar UM token
purga só os endereços daquele token; um item pode ter vários tokens/inquilinos apontando pra ele (não
é o caso do contrato atual, mas o prefixo por token já cobre o caso comum: revogação de token). Purge
por item exigiria uma chave de cache que incluísse o item sem o token — decisão não tomada aqui.

## 5. Simulação local, não a Cloudflare real

Regra da casa para este item: sem acesso à conta Cloudflare real, sem fingir DNS/Cache Rule que não
existem. O que se prova localmente (`scripts/cdn_simulada.py`, HTTP real, sem mock de biblioteca) é o
MECANISMO — cache por caminho sem query string, `Cache-Control` decidindo o TTL efetivo, purge por
prefixo, isolamento de rota de API. A configuração da conta real é `docs/CDN.md`, marcada como
pendente do dono.

## 6. Regra de saída do Cloudflare Free

~1 TB/mês de origem externa é onde o ToS do plano Free passa a pesar (não é um limite técnico
publicado com precisão — é o ponto em que a Cloudflare historicamente entra em contato ou limita
contas Free/Pro com tráfego de "servidor de arquivo"/CDN de mídia pesada). Sem número de tráfego real
de produção ainda, a decisão de migrar para Bunny (PoPs no Brasil, HMAC nativo) ou usar R2 como origem
fica em `docs/CDN.md`, a ser revisitada com o número medido do mês corrente.
